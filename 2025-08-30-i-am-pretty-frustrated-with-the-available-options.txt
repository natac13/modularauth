  The Problem

  Once a JWT is issued with subject data, it can't be updated without reissuing the token. So if a user switches workspaces, we have these options:

  Option 1: Keep Dynamic Data Out of JWT (Recommended)

  The JWT only contains stable identity data, dynamic data is fetched per-request:

  // JWT only has stable identity
  subjects: {
    user: object({
      userId: string(),
      email: string()
    })
  }

  // Workspace comes from your app logic
  const session = await client.getSession()
  const workspace = await getActiveWorkspace(session.user.userId)

  Pros:
  - JWT stays small and cacheable
  - No token reissue needed for workspace changes
  - Clean separation of concerns

  Cons:
  - Extra database lookup for workspace
  - Can't use workspace in Lambda Authorizer directly

  Option 2: Short-Lived Access Tokens with Refresh

  Keep workspace in JWT but use very short access token TTL:

  ttl: {
    access: 60 * 5, // 5 minutes
    refresh: 60 * 60 * 24 * 30 // 30 days
  }

  // Client auto-refreshes and gets new workspace
  const client = createAuthClient({
    onRefresh: async (tokens) => {
      // Token refreshed with current workspace
    }
  })

  Pros:
  - Workspace in JWT for authorization
  - Eventually consistent

  Cons:
  - Frequent refreshes
  - Still has staleness window

  Option 3: Reissue Token Endpoint

  Add an endpoint to reissue tokens with updated subject:

  // New endpoint in auth
  POST /api/auth/reissue
  Authorization: Bearer <current_token>
  Body: { workspaceId: "new-workspace" }

  // Client usage
  await client.updateSession({
    workspaceId: newWorkspaceId
  })

  Pros:
  - Explicit workspace changes
  - Immediate consistency
  - Audit trail of workspace switches

  Cons:
  - More complex
  - Requires explicit action

  Option 4: Claims Endpoint (OIDC Pattern)

  Similar to /userinfo, have a /claims endpoint for dynamic data:

  // JWT has userId only
  // Fetch current claims including workspace
  const claims = await client.getClaims()
  // { userId: "...", workspaceId: "...", permissions: [...] }

  // Can be cached client-side with TTL

  Pros:
  - Standard OIDC pattern
  - Flexible for any dynamic data
  - Can cache with different TTL than JWT

  Cons:
  - Extra request for claims
  - Need to handle caching

  Option 5: Session Layer (Like BetterAuth)

  Add a session concept on top of JWT:

  interface Session {
    token: string // JWT with userId
    workspace: string // Dynamic
    // other mutable state
  }

  await adapter.sessions.updateWorkspace(sessionId, workspaceId)

  Pros:
  - Very flexible
  - Can update anything

  Cons:
  - Adds stateful session management
  - Loses pure JWT benefits

  I think Option 1 + Option 3 gives the best balance:

  1. Default: Keep JWT minimal (userId, email) and fetch workspace from your app
  2. When needed: Provide reissue endpoint for cases where you need workspace in JWT (like Lambda Authorizers)

    subjects: {
      user: object({
        userId: string(),
        email: string(),
        // Optional dynamic fields that can be reissued
        workspaceId: optional(string())
      })
    },

    // Allow reissuing tokens with updated subject
    allowReissue: async (currentSubject, updates, adapter) => {
      // Validate user can access the workspace
      const canAccess = await adapter.users.canAccessWorkspace(
        currentSubject.userId,
        updates.workspaceId
      )

    }
  })

  const client = createAuthClient()

  await client.reissueTokens({
    workspaceId: 'new-workspace-id'
  })

⏺ You're absolutely right! Let's dig into what larger orgs actually do. There ARE claims in the JWT itself, and there's a distinction I should clarify:

  JWT Claims vs Dynamic Claims

  Standard JWT Claims (in the token):
  - sub (subject/userId)
  - iat (issued at)
  - exp (expiration)
  - aud (audience/clientId)
  - Custom claims like email, role, workspaceId

  The problem is these are immutable once issued.

  What Large Orgs Actually Do

  Auth0/Okta Pattern

  They use "Access Token + ID Token + Refresh" with very short-lived access tokens:
  - Access token: 5-10 minutes (with minimal claims)
  - ID token: User profile info (for the client)
  - Refresh token: Long-lived for getting new tokens

  When you switch contexts (like workspace), you refresh to get new tokens with updated claims.

  AWS Pattern

  Uses AssumeRole - you have base credentials, then assume different roles:
  // Base token has userId
  // "Assume" workspace role to get workspace-scoped token
  const workspaceToken = await auth.assumeContext({
    workspaceId: 'workspace-123',
    role: 'admin'
  })

  Slack's Pattern

  They actually use OAuth scopes per workspace:
  - Each workspace has its own token
  - User authorizes per workspace
  - Client manages multiple tokens

  Google's Pattern

  Uses short-lived access tokens + delegation:
  - Access tokens: 1 hour
  - Service can request delegated tokens for specific resources
  - Claims include resource access, not resource identity

  The Enterprise Pattern That Emerges

  Most large systems use what's essentially Option 2 + Option 3 hybrid:
